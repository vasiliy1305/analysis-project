# analysis-project
Проектная работа модуля 6. Рефакторинг кода на Rust

Ниже вас ждёт код проекта, который далёк от идеала. Улучшить в нём можно многое, ведь нет предела совершенству, но проверяться будет исправление конкретных проблем:
+ Использование лишних вызовов clone() вместо ссылок.
+ Использование Rc<RefCell<T>>, там где можно обойтись ссылками.
+ Использование циклов вместо итераторов.
+ Использование unsafe без необходимости.
+ Присутствие singleton, без которого можно обойтись.
Использование излишней валидации вместо tight-типов.
+ Использование вместо дженериков дублирования кода для параметров разных типов.
Использование трейт-объектов в местах, где можно обойтись дженериками.
+ Использование последовательности if вместо одного match.
Присутствие Enum, один из вариантов которого занимает несколько килобайт стека.
Использование паники вместо возврата ошибки.

Порядок исправления несущественен, вес каждого исправления одинаков — нет «более» или «менее» важного.
По легенде, проект достался вам как есть: в нём остались нереализованные возможности и комментарии предыдущего разработчика — это исправлять не требуется. А вот тесты должны продолжать работать, даже если тест-кейсы придётся поправить на другие типы данных.
Вам пригодятся команды:

// `-- --nocapture` позволяет не прятать вывод в терминал (println!() и подобное)
cargo test -- --nocapture
// конкретный тест для запуска можно указать сразу после `test`
cargo test test_all -- --nocapture
// запуск бинарника; в файле с локами те же данные, что и в тестах, - бинарь
// должен остаться работоспособным
cargo run example.log 
В качестве tight-типа можно использовать элементы стандартной библиотеки вроде std::num::NonZeroU32, но можно применить и трейт tightness.

Как работать над проектом
Скачайте файл.
Залейте этот оригинальный (неисправленный) проект в свой публичный репозиторий на GitHub подобно тому, как оформляли проекты раньше.
Осмотрите проект, запустите тесты и исполняемый файл, используя приведённые выше команды.
Найдите проблемный код и сделайте его идиоматическим, не испортив работоспособность программы. Работоспособность проверяйте имеющимися и, при желании, новыми тестами. В коде проекта в комментариях оставлены подсказки в местах, где точно есть плохой код, — его нужно исправить обязательно, это необходимое условие сдачи. Подсказок достаточно на каждый тип проблемного кода из списка выше. Тесты после исправлений должны работать.
Исправьте проблемы. Зафиксируйте изменения в репозитории (одним или несколькими коммитами) и залейте на GitHub. Если ревьюер оставит в Issues замечания — оформляйте исправление каждого замечания отдельным коммитом, в заголовке которого присутствует номер Issue.
Если какой-то тип проблем исправить не получится, а дедлайн будет близко — допускается сдача проекта при 80% исправлений.
Как проверить себя перед отправкой на ревью
Убедитесь, что все тест-кейсы сохранены, тесты проходят, а приложение выводит те же данные, что и раньше.
Минимум 80% проблемы каждого типа из списка, к которым есть комментарии в коде, исправлены.
Обратите внимание:
После исправлений код, вероятно, станет проще.
Не нужно доводить все аспекты проекта до индустриального стандарта: это полезный опыт, но в практике оценивается не это. По легенде, в рамках регулярных работ по уменьшению технического долга вы упрощаете поддержку проекта, после чего тот снова отправляется в долгий ящик, решать свои узкоспециализированные задачи.
Желательно устранить все места, подсвеченные подсказками. У разных людей могут быть разные взгляды на то, что и где улучшать, поэтому подсказки будут общим знаменателем.
Если рискуете выбиться из дедлайна, но лишь 80% проблем из списка исправлено, то можно отправить и так. В реальных проектах с вами наверняка будет случаться что-то подобное.
